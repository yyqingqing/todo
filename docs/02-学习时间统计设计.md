# 学习时间统计 — 需求评估与设计

> 评估时间：2026-10-30
> 需求原文：侧边栏加「学习时间」，点击开始计时、点击关闭停止；进程被杀、关机等异常也记为停止；支持按天/周/月统计，也支持自定义范围。
> 实施状态：**P1 / P2 / P3 已完成**（计时与异常回收、跨天切分与日周月统计、自定义区间、明细列表）。P4 可选，见第九节。
> 结论：需求成立，没有技术拦路石。难点不在统计，而在**"异常也记为停止"这句话背后的时间来源**——这一点定不下来，后面统计全是错的。

---

## 一、结论先行

整体工作量 **2–2.5 人日**（可拆成 4 个阶段，见第九节）。开工前必须定死 3 件事，否则返工：
1. **计时状态归主进程所有，不归页面。** 渲染进程会随窗口隐藏被节流、随 HMR 重挂载、随崩溃消失。计时器只能是主进程里的一份内存状态 + 一行数据库记录，页面只是它的显示器。
2. **"异常停止"要靠心跳，不是靠退出钩子。** 被 `taskkill /F`、断电、蓝屏时没有任何代码会执行。唯一可靠的办法是计时期间每 15 秒把"我还活着"写进库，下次启动时把上次心跳当作结束时间。代价是最多丢 15 秒，收益是绝不把"关机后 8 小时"算成学习。
3. **统计口径必须在纯函数层算，不能在 SQL 里按字符串切。** 会话会跨零点（23:30–00:30 要算成两天各 30 分钟），周起始、月边界、时区都得走本地日历。项目已有的约定是「日期用本地 `YYYY-MM-DD`，时间戳用 UTC ISO」，这里必须沿用。

剩下的是常规工作量：一张表、一组 IPC、一个页面、一个纯 CSS 柱状图。

### 已定决策（2026-10-30）

| #   | 决策        | 取值                                                    | 影响                                                             |
| --- | ----------- | ------------------------------------------------------- | ---------------------------------------------------------------- |
| S1  | 统计维度    | v1 只统计总时长；表里**预置** `plan_id` / `category_id` | 未来按计划/分类统计时只需加 UI 和分组维度，不改 schema、不发迁移 |
| S2  | 休眠 / 锁屏 | 休眠停止（`end_reason='suspend'`），锁屏继续计时        | 睡着不算学习；锁屏但人在（背单词、听音频）仍计入                 |
| S3  | 手动补记    | **不做**，只认用户点「开始计时」                        | 去掉预留的 `source` 列；真要做时加一列 + 一条迁移，代价很小      |

S1 的落地方式值得说明：未来要按计划统计，真正的成本不是加列（SQLite `ALTER TABLE ADD COLUMN` 是 O(1) 的元数据操作），而是**历史数据没有归属**——三个月前的会话你不可能事后补上"当时在学 Java"。所以两列现在就加上，v1 写 `NULL`，UI 上线后新记录开始带值，老记录统一归入「未归类」，不假装能补齐历史。

## 二、需求拆解：其实是两个功能

| 子功能     | 本质                                       | 难点                            | 估时     |
| ---------- | ------------------------------------------ | ------------------------------- | -------- |
| **计时器** | 一个带持久化的秒表，同一时刻只允许一个在跑 | 异常结束的判定与回收            | 1 人日   |
| **统计**   | 把会话切成时间段再聚合                     | 跨天切分、周/月边界、自定义范围 | 1 人日   |
| 页面与导航 | 侧边栏一项 + 一个三卡页面                  | 无                              | 0.3 人日 |

**关键判断：这两个功能的数据源是同一张明细表，不要为了统计单独建汇总表。** 理由见第四节。

## 三、计时器：时间到底从哪来

### 3.1 状态机

```
idle ──start()──> running ──stop()/quit/suspend/crash──> stopped
                    ↑                                      │
                    └────────── 同一行不允许重开 ───────────┘
```

- 同一时刻只允许一行 `status = 'running'`，用**部分唯一索引**强制（见第四节），不靠代码自觉。
- 开始计时 = 立刻插入一行（`status='running'`, `last_seen_at = started_at`），而不是等停止时才写。**先落库再计时**，否则杀进程时连"开始过"都不知道。

### 3.2 心跳

计时期间每 **15 秒** `UPDATE study_session SET last_seen_at = ?`。
- 为什么是 15 秒：SQLite 单行更新 + WAL，开销可忽略；断电最多丢 15 秒，用户感知不到。
- 为什么不每秒写：写放大没有收益，1 秒的精度对"学习时长"没有意义。
- 心跳由主进程的 `setInterval` 驱动，和渲染进程是否可见无关。

### 3.3 结束时间的三种来源

| 场景                                  | 谁写的                 | `ended_at` 取值 | `end_reason` |
| ------------------------------------- | ---------------------- | --------------- | ------------ |
| 用户点「结束计时」                    | 主进程                 | 当前墙钟        | `manual`     |
| 正常退出应用                          | `before-quit`          | 当前墙钟        | `quit`       |
| 系统休眠 `powerMonitor.suspend`       | 主进程                 | 当前墙钟        | `suspend`    |
| 进程被杀 / 崩溃 / 断电 / 关机来不及写 | **下次启动的回收逻辑** | `last_seen_at`  | `crashed`    |

回收逻辑放在 `openDatabase()` 之后、建窗口之前执行：

```sql
UPDATE study_session
   SET ended_at = last_seen_at,
       duration_seconds = CAST((julianday(last_seen_at) - julianday(started_at)) * 86400 AS INTEGER),
       status = 'stopped',
       end_reason = 'crashed',
       updated_at = ?
 WHERE ended_at IS NULL
```

这条 `UPDATE` 是幂等的：没有残留行时影响 0 行。

### 3.4 时钟：墙钟记录，单调时钟计量

`Date.now()` 会被 NTP 校时、用户手动改时间、虚拟机快照回滚搞乱，直接相减可能得到负数或荒谬值。
- 运行时计时用 `process.hrtime.bigint()` 算增量（单调，不受系统时间影响）；
- 落库的 `started_at` / `last_seen_at` 用墙钟（跨进程恢复只能靠它）；
- 停止时若单调时长与墙钟时长偏差 > 60 秒，以**单调时长**为准，并在 `note` 里留一句"检测到系统时间变化"（可选，先不做也行）。

### 3.5 睡眠与锁屏

`powerMonitor` 在 Windows 上能稳定拿到 `suspend` / `resume`，锁屏事件在部分版本上不可靠。
- 默认：`suspend` 立即收尾（`end_reason='suspend'`），`resume` 后**不自动续计**。理由：睡觉 8 小时不该算成学习 8 小时，用户醒来看到"今日学习 8 小时"会失去对数据的信任。
- 设置项「休眠后自动继续计时」默认关闭；真要做，也是在 `resume` 时新开一行，而不是把睡眠时间补进上一行。
- 锁屏**不停止**计时（S2）：锁屏期间人可能还在背单词、听音频；真正离开的标志用休眠/关机来判定。

## 四、数据模型

### 4.1 新表 `study_session`（迁移 `003-study-time`）

```sql
CREATE TABLE study_session (
  id               TEXT PRIMARY KEY,
  started_at       TEXT NOT NULL,              -- UTC ISO，本地日期由它派生
  last_seen_at     TEXT NOT NULL,              -- 心跳，UTC ISO；崩溃时当结束时间用
  ended_at         TEXT,                       -- NULL = 仍在进行（或待回收）
  duration_seconds INTEGER NOT NULL DEFAULT 0, -- 结束时固化，避免统计反复相减
  status           TEXT NOT NULL DEFAULT 'running',  -- running | stopped
  end_reason       TEXT NOT NULL DEFAULT 'running',
  -- running | manual | quit | suspend | crashed
  -- S1 预留：v1 恒为 NULL，将来做"按计划/分类统计"时开始写入。
  -- ON DELETE SET NULL：计划被删后时长仍然保留，归入"未归类"，历史不会消失
  plan_id          TEXT REFERENCES plan(id) ON DELETE SET NULL,
  category_id      TEXT REFERENCES category(id) ON DELETE SET NULL,
  note             TEXT,
  created_at       TEXT NOT NULL,
  updated_at       TEXT NOT NULL
);

CREATE INDEX idx_study_started ON study_session(started_at);
CREATE INDEX idx_study_plan ON study_session(plan_id);
CREATE INDEX idx_study_category ON study_session(category_id);
-- 同一时刻只允许一个正在计时的会话：靠约束，不靠代码自觉
CREATE UNIQUE INDEX idx_study_running ON study_session(status) WHERE status = 'running';
```

**几个字段的理由：**
- `duration_seconds` 冗余存一份：统计接口 90% 的查询是"这段区间的总秒数"，每次用 `julianday` 相减既慢又容易被时区/精度问题坑。结束即固化，回收时也一并算好。
- `status` 单独一列而不是用 `ended_at IS NULL` 判断：为了让部分唯一索引成立（SQLite 里多个 NULL 在唯一索引中互不冲突，`ended_at` 上做不了这个约束）。
- `end_reason` 是**产品功能**不是调试信息：明细列表要标"异常结束"，统计里要能选"是否计入睡眠时段"。
- `plan_id` / `category_id` 是 S1 的预留位：只加列不加索引会拖慢按维度统计，所以索引一起建好；v1 不写值，查询里按 `NULL = 未归类` 处理。

### 4.2 为什么不做 `study_daily` 汇总表

- 量级：一天 2–5 次会话，一年约 1 千行，十年也不到 1 万行。SQLite 对这种表做区间扫描是毫秒级。
- 汇总表要和明细保持一致：补记、编辑、删除、跨天切分都要级联维护，多一处就可能对不上。
- 真到需要预聚合的量级（几十万行），再加一个物化表或按天视图，不影响现有 schema——`study_session` 仍然是唯一事实来源。

### 4.3 与现有数据的关系

- **只连外键，不留快照。** `plan_id` / `category_id` 指向当前计划：改名后统计显示新名字（符合直觉），删除后 `ON DELETE SET NULL` 归入「未归类」，时长本身不丢。
  这和 `todo_item` 保留 `title` 快照的做法不同，是有意的：待办是**历史事件**（"那天我要做的那件事"），改名必须保留当时的名字；学习时长是**时间资源**（"这两个小时的归属"），归属跟着实体走更合理。
- **统计层按「可分组」写**：v1 只实现按时间分桶，但聚合函数接受 `groupBy`（`'day' | 'plan' | 'category'`），未来加维度只是补一个 key 提取器和筛选器，不重写聚合逻辑。
- 与积分系统暂不打通。若要做"学习满 1 小时 +N 分"，用现有的 `score_ledger`（`source_type='study_session'`, `source_id=会话 id`），幂等键现成。

## 五、异常场景矩阵

| 场景                  | 发生什么                                     | 数据结果                      | 用户看到                             |
| --------------------- | -------------------------------------------- | ----------------------------- | ------------------------------------ |
| 点「结束计时」        | 主进程写 `ended_at`                          | 精确到秒                      | 正常一条                             |
| 点关闭按钮（缩托盘）  | 计时**继续**                                 | 不动                          | 侧边栏/页面仍显示计时中              |
| 退出应用（托盘→退出） | `before-quit` 收尾                           | `end_reason='quit'`           | 下次打开显示"上次计时随应用退出结束" |
| 任务管理器结束进程    | 什么都没写                                   | 下次启动回收到 `last_seen_at` | 明细标「异常结束」                   |
| 直接断电/蓝屏         | 同上一行                                     | 同上，最多丢 15 秒            | 同上                                 |
| Windows 关机          | 大概率触发 `before-quit`；来不及则按崩溃回收 | `quit` 或 `crashed`           | 同上                                 |
| 系统休眠              | `suspend` 收尾                               | `end_reason='suspend'`        | 明细标「休眠结束」                   |
| 用户改系统时间        | 单调时钟兜底                                 | 时长仍然正确                  | 无感知                               |
| 渲染进程崩溃/刷新     | 主进程不受影响                               | 不动                          | 页面重连后继续显示计时               |
| 应用被重复启动        | 单实例锁已存在，第二个进程直接退出           | 不产生第二行                  | 无感知                               |

**"异常也记为停止"的实现要点：不是捕获异常，而是让"没有正常结束"这件事在下次启动时必然被发现。** `ended_at IS NULL` 就是那个发现条件。

## 六、统计口径

### 6.1 切分规则（纯函数，可单测）

- 输入：会话列表（UTC ISO 时间戳）。
- 输出：`{ localDate: 'YYYY-MM-DD', seconds }` 片段数组。
- 跨零点的会话按本地 0 点切开：`23:30–00:30` → `10-29: 1800s` + `10-30: 1800s`。
- 周：ISO 周，**周一起始**，key 形如 `2026-W44`。
- 月：自然月，key 形如 `2026-10`。
- 不用 `86400` 硬除，按本地日历推进（中国无夏令时，但代码不该假设这一点）。

放在 `src/shared/domain/study.ts`，和 `progress.ts`、`score.ts` 同级，Vitest 覆盖：
跨天、跨周、跨月、零长度会话、负时长（时钟回拨）保护、空范围补零。

### 6.2 查询接口

```ts
stats({ from: '2026-10-01', to: '2026-10-31', granularity: 'day' })
→ {
    totalSeconds, sessionCount, longestSeconds, averageSeconds,
    buckets: [{ key, label, seconds, sessionCount }]   // 空桶补 0，保证柱状图连续
  }
```

- 粒度默认按范围自动选：≤ 31 天按天、≤ 26 周按周、否则按月；也允许用户手动切。
- 自定义范围就是 `from`/`to` 两个本地日期（闭区间），上限建议 5 年（防误输入 `1900`）。
- 签名里预留可选 `groupBy?: 'day' | 'plan' | 'category'`（S1）：v1 只实现时间维度，传 `plan` 时不报错、退回时间维度并忽略，避免以后加维度要改协议。

### 6.3 展示指标

总时长 / 日均 / 会话数 / 最长一次 / 平均每次。日均 = 总时长 ÷ 范围天数（不是 ÷ 有记录的天数，否则"只学一天"会显示成日均 8 小时）。

## 七、IPC 契约（沿用现有 `Api` 形状）

```ts
study: {
  start(): Promise<StudyStatus>
  stop(): Promise<StudyStatus>
  status(): Promise<StudyStatus>
  // StudyStatus = { running: boolean; startedAt: string | null; elapsedSeconds: number }
  sessions(range: { from: DateString; to: DateString }): Promise<StudySession[]>
  stats(query: StudyStatsQuery): Promise<StudyStats>
}
```

- 计时**不进**每秒 IPC：渲染进程拿 `status()` 的快照（含 `elapsedSeconds`）后自己本地 tick，窗口重新可见时再拉一次校正。
- 状态变化通过现有 `data:changed` 广播（实体名加 `'study'`），悬浮窗/其他页面同步刷新。
- 窗口隐藏时 Chromium 会节流 `setInterval`，页面上的秒数可能跳变——真实时长在主进程，不受影响；回来时重新对齐。

## 八、界面设计

### 8.1 侧边栏

```ts
{ to: '/study', label: '学习时间', icon: Timer }   // 放在「积分」之后
```

计时中在标签后显示一个小圆点或 `mm:ss`，让用户切到别的页面也知道还在计时。

### 8.2 页面三块（四态齐全：加载/空/错误/无数据）

1. **计时卡**：大号 `HH:MM:SS`（`tabular-nums`，等宽不跳动），主按钮「开始计时 / 结束计时」，旁边显示今日累计。计时中给一个克制的呼吸点，不要花哨动画。
2. **统计卡**：预设 chips（今天 / 本周 / 本月 / 自定义）+ 自定义日期区间；指标行；柱状图。
3. **明细卡**：最近 20 条会话，时间、时长、结束原因；异常结束的显示「异常结束 · 按最后心跳 15:03 记」。

### 8.3 图表：不引第三方库

项目现在零图表依赖，为了一个柱状图引入 ECharts/Recharts（几百 KB）不划算。用 `div` 高度百分比 + `tokens.css` 里的品牌色画柱，交互只做 hover 显示数值。柱状图对"时长趋势"这个场景已经够用。

## 十、风险与未决问题

### 风险

1. **`powerMonitor` 的可靠性**：Windows 上 `suspend` 事件偶发丢失。兜底是心跳——即使没收到 suspend，恢复后的心跳间隔会暴露异常，可以在回收时判定"间隔 > 5 分钟 = 疑似休眠"并截断。
2. **用户忘记停止**（S3 决定不做补记之后，这个风险更高了）：挂机 10 小时会被如实记录，用户只能看着一个荒唐的总时长。P3 加一个"单次会话超过 4 小时"的确认提示（不自动截断，避免偷偷改用户的记录）。
3. **多显示器/多时区**：用户在 UTC+8 用，出差到 UTC+0，同一批历史数据的"日期"会按当前时区重新解释。可接受（项目已有约定），但统计页要显示"按本地时区统计"。

### 还没定的问题

1. **超长会话**（> 4 小时）是弹确认、自动截断，还是不管？我倾向弹确认。
2. **计时要不要出现在悬浮窗/托盘**？悬浮窗加一行"学习中 00:12:34"很自然，但会挤占今日清单空间。
3. **要不要学习目标**（每天/每周目标时长 + 进度条）？这属于另一个功能，可以后置。
4. **P1 做到哪为止**：只做后端 + 一个最小可用页面，还是连统计一起做完？
