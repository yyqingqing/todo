## 一、结论先行

需求成立，技术上没有拦路石。但有 3 处必须开工前定死，否则地基会歪：
1. **"任务分类"和"计划"是两种东西，需求里混成了一个。** 必须拆成 `分类 / 计划 / 任务 / 每日待办` 四层，否则第 2 条的嵌套计划和第 6 条的积分统计互相打架。
2. **"桌面顶端固定 + 透明不遮挡"有 3 种物理形态**，实现成本差 5 倍以上，需要指认是哪一种。
3. **第 7 条顺延的语义没定义**：原日期要不要留痕、要不要自动顺延。这决定数据库结构和全部统计口径。

剩下 4 条是常规工作量。真正需要控制的是日历页和积分页的视觉野心，而不是功能本身。

工作量粗估：完整 v1 约 **12–17 人日**，砍到 MVP 约 **7–9 人日**（详见第六节).

## 二、需求重构：把 4 个概念拆开

需求原文："支持用户定义不同的任务，也就是任务可以分类，比如用户制定了为期 3 个月的学习 java 的计划"。

这句话把 4 个概念压成了 1 个，拆开后是这样：

| 概念                  | 职责                         | 例子                         | 关键属性             |
| --------------------- | ---------------------------- | ---------------------------- | -------------------- |
| **分类** Category     | 横向筛选维度、配色、统计口径 | 学习 / 工作 / 生活           | 名称、颜色           |
| **计划** Plan         | 有起止时间的容器，**可嵌套** | 3 个月 Java 学习             | 起止日、父计划       |
| **任务** Task         | 原子可执行项                 | 读完《Java 编程思想》第 3 章 | 预估分钟、所属计划   |
| **每日待办** TodoItem | 任务在**某一天**的实例       | 今天要做的那一章             | 日期、状态、顺延痕迹 |

**为什么必须拆（不是洁癖，是功能会挂）：**
- 计划要算完成度（"Java 计划完成 40%"），分类要算投入占比（"本月学习类完成 30 项"）。混成一个实体，这两个数都算不出来。
- 第 2 条要求"计划下展开小计划"，说明计划是**树**；而分类是**平的**。树和平的混在一起，UI 就没法设计。
- 第 7 条要求"未完成项挪到明天"，说明"任务是什么"和"某天要做它"是两件事。否则改日期就把历史抹掉了，第 6 条的积分和统计全部失真。

**一个容易被忽略的设计判断：今日待办必须允许"无归属的临时事项"。**

如果用户想记"下午给张三打电话"却必须先建计划，摩擦太大，应用三天就被弃用。所以 `todo_item.task_id` 必须可空。

## 三、逐条评估

### 需求 1 + 2：计划与嵌套小计划 —— 合理，注意 3 个坑

- **层级**：数据库用 `parent_id` 自引用，支持任意深度；但 **UI 建议按 2–3 层设计**（3 个月计划 > 第 1 周计划 > 具体章节），超过 3 层缩进在 PC 分辨率下会不可读。
- **完成度口径**：只统计**叶子任务**（`done / (done + open)`，排除已放弃的），父计划完成度由子项汇总，**不要给父计划单独加权**。否则"父计划 50% + 子计划 50%"会出现 75% 这种没人能解释的数字。
- **计划完成时机**：建议**手动点"完成计划"**，系统提示"还有 2 项未完成，确认结束？"。如果做成"子任务全 done 就自动完成"，那么用户删掉一个未完成任务会导致计划突然完成并触发积分，出现"删任务反而加分"的荒谬路径。

### 需求 3a：今日 todo 清单 —— 常规工作量

必须有的功能点（很容易漏）：
- 回车即新增、自动聚焦下一条（录入速度决定这个应用能否活下来）
- 勾选完成 / 取消完成（幂等，见积分一节）
- 从计划里"拉"任务到今天（双向：也可以在计划里给任务排期）
- 手动拖拽排序
- 顶部进度条（3/8）
- 未完成项 → 顺延入口（需求 7）
- 时间边界处理：跨零点后"今天"要自动切到新的一天

### 需求 3b：桌面悬浮窗 —— 全项目技术难点，见第五节

### 需求 4：sqlite —— 没问题，但有 4 个硬约束

1. **`scheduled_date` 存本地日历日字符串 `YYYY-MM-DD`**，不要存 UTC 时间戳。跨零点、夏令时、以后跨设备同步，全部依赖这个决定。
2. `created_at` / `completed_at` 存 UTC ISO 字符串，两者分开。
3. 开 **WAL 模式**，写入走单一连接串行（Electron 主进程天然串行；Tauri 用 `Mutex<Connection>`）。两个窗口同时写不能出现 `database is locked`。
4. 建 `schema_version` 表做迁移，别用"删库重建"应付 schema 变更——用户数据会丢。

### 需求 5：日历 —— 需求描述最模糊，需要明确"显示什么"

"支持日历显示"可以有 4 种信息密度，成本差很远：

| 方案         | 单元格内容                             | 成本    | 价值         |
| ------------ | -------------------------------------- | ------- | ------------ |
| 最简         | 只高亮有 todo 的日期                   | 0.5 天  | 低，不如不做 |
| 推荐（v1）   | 完成度圆环 + **计划跨度条** + 顺延标记 | 2 天    | 高           |
| 进阶（v1.5） | 上面 + 可拖拽改期                      | +1.5 天 | 中           |
| 完整（v2）   | 周视图 / 年视图 / 时间轴               | +3 天   | 低           |

**关键判断：计划跨度条必须有。** 只显示完成率圆点，用户感受不到"我正处在 3 个月 Java 计划的第 3 周"，日历就失去意义了。跨度条是甘特图的降级形态，跨多天的横向色块，是这个页面唯一有辨识度的东西。

### 需求 6：积分 —— 建模是后端活，你会很快；难的是规则设计

先明确一件事：**这是纯经验值（XP），没有消费场景。**"积分"这个名字容易让人期待商城，实际上它只承担正反馈。这点定了，系统就简单了。

**技术要点（4 条，全是踩过的坑）：**
1. **流水表 append-only**，不改不删，永续追加。
2. **唯一约束保证幂等**：`UNIQUE(source_type, source_id, reason)`。否则用户"勾选 → 取消 → 再勾选"会加两次分。
3. **撤销用冲正，不用删除**：取消完成任务时追加一条负分记录，保留审计轨迹。
4. **补录的归属**：昨天完成的任务今天才勾，分记在 `occurred_at`（实际完成时间），入账日 `settled_date` 另记。否则跨月统计会错位。

**产品要点（比技术更重要）：**
- 分值必须体现"按时完成 > 逾期完成"，否则顺延没有成本，第 7 条就退化成无意义的挪列。
- "每日全清"奖励要用**完成率**判定，不要用绝对条数——否则诱导用户往清单里塞简单事项凑数。

推荐默认规则（全部可配置，先给一套能跑的）：

| 事件                | 分值 | 条件                          |
| ------------------- | ---- | ----------------------------- |
| 完成一条当日待办    | +10  | `scheduled_date == 完成日`    |
| 逾期后补完          | +6   | 跨天补录，打折                |
| 当日清单全清        | +20  | 完成率 100% 且条数 ≥ 3        |
| 计划整体完成        | +80  | 手动确认完成计划时一次性      |
| 连续 7 天有完成记录 | +50  | streak 奖励，每日最多触发一次 |

**积分页应该长这样**：上半部是流水明细（时间 / 事项 / 原因 / 分值），下半部是聚合——日历热力图（GitHub 贡献图那种）+ 分类占比 + 累计曲线。热力图是这个页面唯一的视觉亮点，值得花时间。

### 需求 7：顺延 —— 语义必须现在定义

未完成项挪到明天/未来某日。有 3 个正交的决策点：

| 决策     | 选项               | 推荐                             | 理由                                                             |
| -------- | ------------------ | -------------------------------- | ---------------------------------------------------------------- |
| 触发方式 | 手动 / 自动 / 混合 | **手动（默认）+ 设置项可开自动** | 自动顺延会让清单只增不减，用户永远在还昨天的债，完成率统计也失真 |
| 数据动作 | 移动 / 复制        | **移动**                         | 复制会产生大量幽灵记录，且"这条到底算哪天完成的"永远说不清       |
| 是否留痕 | 留 / 不留          | **留**                           | 不留痕就无法统计"平均顺延次数"，也无法做下面的降级提醒           |

**建议的留痕字段**：`origin_date`（最初计划的日期）、`rollover_count`（顺延次数）、`rollover_log`（每次顺延的 from/to 记录）。

留痕的**产品价值**：清单里对 `rollover_count >= 3` 的项做视觉降级（变灰 / 加提示"已顺延 3 次，要拆小一点或放弃吗"）。这是在帮用户做减法，不是记账。

**必须补一个需求里没写的操作：放弃 / 归档。** 只允许"完成"和"顺延"，清单会无限膨胀，最终用户会因为"欠债感"弃用应用。允许体面地结束一件事，是这类工具的核心体验。

## 四、桌面悬浮窗：三种形态，成本差 5 倍

这是全项目最贵的选择题，必须你指认。

| 形态                | 实际效果                                                         | 实现方式                                                           | 成本                 | 平台         |
| ------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------ | -------------------- | ------------ |
| **A. 置顶悬浮窗**   | 浮在所有窗口之上，半透明，可拖动，可点击穿透                     | `alwaysOnTop` + `transparent` + `setIgnoreMouseEvents`             | **低**（0.5–1 天）   | Win/mac 通吃 |
| **A'. 顶部固定条**  | A 的变体，吸附屏幕顶边，像自制的状态栏                           | A + 无边框 + 定位到工作区顶部                                      | 低（A 之上 +0.5 天） | 同上         |
| **B. 贴桌面壁纸层** | 像 Rainmeter 那样嵌在桌面图标层，被其它窗口遮住，按 Win+D 才看见 | Win32：`FindWindow("Progman")` → 找到 `WorkerW` → `SetParent` 挂载 | **高**（3–5 天）     | 仅 Windows   |

B 形态的额外代价（容易被低估）：
- Explorer 重启后挂载丢失，要监听并重新挂载
- Win11 各版本的 `WorkerW` 层级结构不一致，要逐个适配
- 挂载后窗口的鼠标事件、焦点、DPI 行为都变得古怪，调试极其痛苦
- 跨平台为 0（macOS 没有等价机制）

**我的判断**：你说的"置于桌面顶端固定，背景可设置透明不遮挡"，按中文语义 90% 是 **A'**（屏幕顶部一条，半透明浮在窗口上方），而不是 B（贴壁纸层）。B 的用户通常会形容成"像 Rainmeter 那样贴桌面上"。

**无论选 A 还是 A'，这 4 件事必须做，否则悬浮窗会成为负担：**
1. **点击穿透开关（"锁定"模式）**：锁定后鼠标事件穿透到底层窗口，只能看不能点；解锁才能拖动和勾选。没有这个，悬浮条会不停抢鼠标，比不用还烦。
2. **全屏自动隐藏**：检测到用户在看视频 / 开会 / 打游戏时自动隐藏。`alwaysOnTop` 会盖在 PPT 放映和视频全屏上面，这是置顶窗最容易翻车的地方。
3. **不抢焦点**：悬浮窗显示时不激活应用，用户正在打字时不能被抢走光标。
4. **位置 / 尺寸 / 透明度持久化**，并按显示器分别记忆（多屏 + DPI 缩放场景）。

## 五、技术选型

### 约束条件

- 你的前端是弱项 → 需要能快速看到效果、出错好排查的方案
- **本机没有 Rust**，装 Rust + VS Build Tools 约 4GB 磁盘、30–60 分钟，国内网络还要配镜像
- 应用要**长期常驻桌面** → 体积和内存不是纸面参数，是真实体验
- 需要 sqlite + 两个窗口（主界面 + 悬浮条）

### 三个候选

| 维度               | Electron 33+                  | Tauri 2                           | PySide6                       |
| ------------------ | ----------------------------- | --------------------------------- | ----------------------------- |
| 安装包             | ~120 MB                       | ~10 MB                            | ~80 MB                        |
| 常驻内存           | ~200 MB                       | ~70 MB                            | ~100 MB                       |
| 首次环境准备       | ✅ Node 已就绪，`pnpm i` 即可 | ❌ 装 Rust + MSVC（4GB / 1 小时） | ✅ pip 即可                   |
| 透明 + 置顶 + 穿透 | ✅ API 成熟，示例最多         | ✅ 支持，Windows 偶发黑底需调     | ✅ 支持，但样式定制痛苦       |
| 形态 B（贴壁纸层） | 需自写 native addon           | 需自写 Win32 FFI                  | ✅ pywin32 最省事             |
| 前端生态           | React / Vue 全量              | 同左                              | QSS，用不了 Tailwind / 组件库 |
| 你的技能匹配       | JS/TS 中等                    | Rust 零基础                       | Python 强                     |
| 调试体验           | ✅ DevTools 全套              | 一般（Rust 编译错误劝退）         | 一般                          |

### 推荐：Electron + React + TypeScript + better-sqlite3

理由按权重排：
1. **立刻能跑。** Node 22 + pnpm 已就绪，`git init` 之后半小时内能看见第一个置顶透明窗。Tauri 在这个项目上要你先花一小时装环境，而那正是验证需求是否成立的阶段。
2. **形态 A/A' 是 Electron 最成熟的用法**，透明窗、置顶、穿透、全屏检测全有现成 API 和大量踩坑记录。Tauri 在 Windows 下的透明 WebView2 有已知的偶发黑底问题，排查成本对弱前端不友好。
3. **代价只有体积和内存**，且这是本地效率工具，用户就是你自己，120MB 安装包不致命。

**什么情况下改选 Tauri**：你愿意花一小时装工具链，并且确认最终产品是长期常驻、很在意那 130MB 内存差。收益是包小 10 倍、启动快一倍。

**什么情况下改选 PySide6**：只有你坚持要形态 B（贴壁纸层）时才值得考虑，因为 pywin32 做 `SetParent` 最简单。但代价是放弃整个 Web 前端生态——你的弱项会瞬间变成强需求。不推荐。

**明确排除的方案：纯 Web / PWA。** 浏览器没有置顶和透明能力，需求 3 直接不成立。

### 一个低成本、高回报的架构约束

**把"壳"和"业务"彻底分层。**

```
src/
  domain/      纯 TS：计划树、顺延规则、积分计算、统计口径。不 import 任何 Electron API
  data/        repository 层：SQL 语句、迁移脚本
  shell/       Electron 主进程：窗口控制、托盘、IPC、数据库连接
  ui/          React 渲染进程：只调用 IPC，不含业务规则
```

好处：万一以后要换 Tauri、或者想加个 Web 预览版，`domain/` 一行不用改。这个约束现在几乎不花成本，以后能救命。

## 六、范围划分

### MVP（7–9 人日）—— 能自己每天用起来的最小闭环

1. 脚手架 + sqlite + 迁移 + domain 层地基（1–2 天）
2. 计划树 CRUD（含嵌套 + 分类）（2 天）
3. 今日 todo + 从计划拉取 + 勾选（1.5 天）
4. 顺延（单个 / 批量到指定日期）（1 天）
5. 悬浮条：置顶 + 透明 + 穿透 + 全屏隐藏 + 位置记忆（1.5 天）
6. 托盘 + 开机自启（0.5 天）

### v1（+5–8 人日）—— 完整需求

7. 日历月视图：完成度 + 计划跨度条（2 天）
8. 积分流水 + 统计页（热力图 / 分类占比）（2 天）
9. 四态补齐（加载 / 空 / 错误 / 无数据）+ 暗色 + 视觉自检（2–3 天）

### v1.5 候选（明确延后）

- 周期任务（每天 / 每周固定事项）—— 见下方风险 1
- 日历周视图、拖拽改期
- 系统通知提醒
- 数据导出 / 自动备份到网盘目录

### 明确不做

- 多人协作 / 账号体系
- 跨设备同步（但 schema 用 UUID 主键 + UTC 时间，给未来留门）
- 时间块 / 番茄钟 / 计时器
- 积分商城 / 消费
- 无限层级子任务视觉
